# English AI 项目面试笔记

这篇用于口头演练。回答时按“业务问题 → 当前实现 → 为什么这样做 → 边界和改进”展开；只有自己实际负责并能现场解释的内容，才用“我设计、我实现”描述。

## 一分钟项目介绍

English AI 是一个英语学习项目，覆盖词库查询、课程学习、学习记录、AI 对话和邮件提醒。代码用 pnpm workspace 管理，前端是 Vue 3，后端分为 NestJS 主 API 和 AI 两个应用，业务数据用 Prisma 访问 PostgreSQL，聊天历史由 PostgresSaver 单独维护。

技术上可以展开四点：支付通过验签、订单核对和数据库条件更新处理重复回调；AI 对话通过 SSE 展示增量并按角色隔离前端状态；发音通过腾讯 TTS 与 MinIO 缓存复用音频；账号注销按顺序清理队列、聊天检查点和业务关联数据。项目还存在学习统计事务、Socket 身份验证等改进点，我会明确区分现有实现与后续方案。

## 高频问答

### 1 为什么拆两个后端应用

主 API 负责交易和学习数据，AI 应用负责模型流和摘要任务，职责与运行入口比较清晰。它们共享基础设施封装和业务数据库，并通过 HTTP 通知任务重排。现阶段是双应用拆分，还没有服务发现、网关治理或完善分布式追踪，不能单靠两个端口称为成熟微服务架构。

追问共享库是不是单例：每个 Nest 应用各有自己的依赖注入容器，跨进程不会共享一个 JavaScript 对象；跨进程协调依赖数据库或 Redis。

### 2 支付回调来了两次怎么办

先验签，再核对 appId、可配置的 sellerId、订单号、金额和支付状态。结算事务用条件 updateMany，只更新未成功订单；返回 count 为 0 就不重复授予权益。第一次更新成功才 upsert CourseRecord，事务提交后推送 Socket 通知。

关键是数据库里的条件更新和唯一约束，不是进程内布尔锁。可以画出两个并发回调竞争同一订单的过程，解释为什么“先 SELECT 再无条件 UPDATE”存在竞争窗口。

追问能否避免重复扣款：不能只靠权益幂等保证。当前仍可能创建多个待支付订单，需要额外的待支付订单复用和平台对账设计。

### 3 支付回调丢了或 Socket 断了怎么办

状态接口先查本地权益；没有权益时，在限定候选订单范围内调用支付宝查单，验签并核对订单与金额，再复用 settle。Socket 只是刷新提示，数据库和支付平台才是判断来源。平台不可用时返回未确认，不让用户误以为必须重新付款。

追问是不是最终一定一致：目前是用户查询触发的补偿，没有完整定时对账或通知 outbox，不能承诺所有无人查询订单都会自动补齐。

### 4 为什么 AI 对话用 SSE

浏览器先 POST 一次问题，后面主要是服务器持续推送文本增量，SSE 足够表达这个方向。项目用 fetch-event-source 支持 POST、Authorization 和 AbortController。服务端发送 data JSON 加空行，并区分 chat 与 reasoning。

追问为什么最后一次性出现：检查每一层 Nginx 是否开启缓冲，再确认服务端是否及时 write、客户端是否持续追加；不能仅看模型设置 streaming true 就认定链路已经流式。

### 5 切换角色后怎样防止回复串台

每个 role 有独立 Conversation，包括消息数组和 controller。发起请求时捕获具体 state 与目标消息对象，chunk 写入这个对象，而不是写到“当前选中的角色”。A 生成期间切换 B，A 继续后台更新；切回 A 不用历史请求覆盖正在生成的数据。

追问 abort 是否够：不够。已经完成或不能取消的异步步骤仍可能回调，所以还要检查对象身份或 revision。页面刷新和 tracker 注册都使用了同类思想。

### 6 对话历史如何隔离

服务端从通过 Guard 的 req.user 获取身份，覆盖客户端 body 中的 userId，使用 userId-role 组成 thread_id。PromptService 先确认角色属于当前用户且没有被删除，再读写历史。

追问编辑旧消息是否回滚历史：当前只截断前端展示，服务端仍追加新消息，因此不能声称已实现完整会话分支或历史回滚。下一步应定义稳定消息 ID 和 checkpoint 分支策略。

### 7 自定义 Agent 删除后为什么不重新出现

默认 Agent 是代码中的默认列表，用户修改与删除用 ChatAgent 覆盖记录表示。删除默认项时保留 deleted 标记，列表合并时隐藏它；若直接删覆盖行，会恢复为默认角色。用户与 role 的复合唯一键限制同一角色的覆盖记录。

追问删除是否清除历史：当前 remove 仅隐藏角色，未删除该角色 checkpoint；账号注销才清理用户全部历史。产品语义需要明确。

### 8 你做的是 RAG 吗

当前是博查搜索结果拼接到提示词的搜索增强，没有文档切块、Embedding、向量库召回或重排。普通聊天 Agent 也没有学习数据库工具，queryTool 在日报 Agent 中。可以继续演进检索链路，但不能把未来架构写进现有经历。

### 9 双 Token 的有效期是什么

当前两者都是 7 天，通过 tokenType 区分用途。Guard 验签、检查类型并查询账号是否存在；refresh 接口只接受 refresh 类型。通常短 access、长 refresh 更便于限制暴露窗口，但当前配置还没分开。

追问刷新失败怎么办：业务 Axios 的等待队列只有成功回调，失败可能让请求悬挂。可以改成统一 single-flight Promise，让所有等待者一起 resolve 或 reject，增加单次重试和会话版本检查。AI 请求已有独立 pendingRefresh，但并非全应用统一锁。

### 10 学习记录会不会重复

数据库 userId-wordId 唯一键限制重复记录，保存前也会查询已存在单词。但当前记录写入和 wordNumber 更新不在一个事务里，仍可能部分成功；并发预查也不能代替约束。

改进时先校验并去重输入，再把实际新增记录数与计数更新放进事务。打卡唯一键是 userId-date，dayNumber 表示累计天数，不是连续天数。不能只因为 increment 是原子操作，就说整条学习链路原子。

### 11 为什么发音要经过后端

后端能保护 TTS 凭证、限制只能合成词库单词，并用单词和音色等参数生成稳定缓存键。先读 MinIO，缺失才合成；同一进程的相同请求复用 Promise，避免重复调用。存储故障时不盲目回源，防止失去缓存后持续付费。

追问多实例怎么办：pending Map 和限流 Map 都只在进程内。要跨实例合并和限流，需要 Redis 等共享协调或其他一致性设计。

### 12 移动端点击喇叭为什么有时没声音

如果先 await 获取音频再调用 play，可能失去用户点击激活。当前直接在点击同步阶段创建同源 Audio 并 play，后端支持 Range；前端处理 loading、waiting、超时和 NotAllowedError，并确保切词停止旧音频。真实 Safari 行为仍要在设备上验收。

### 13 定时邮件能保证只发一次吗

不能这么说。jobId 可以限制同 ID 任务重复入队，但处理失败后的重试、SMTP 接受后响应丢失等场景仍可能重复。当前邮件任务也没有显式 attempts/backoff。

报告目前提前生成再延迟发送，可能不包含发送前新增学习记录。更合理的演进是在到期任务中读取指定业务日期数据，并维护发送状态；邮件失败必须抛给队列，不能吞错让任务变 completed。

### 14 注销为什么不能只删 User

还存在 Redis 中待发的日报和另一个数据库里的聊天 checkpoint。当前先拿账号独占锁，检查并清理任务，在聊天库事务中删历史，最后删业务用户并级联关联表。聊天和发送邮件使用共享锁与注销协调。

追问是不是跨库事务：不是。外部步骤失败会保留账号方便重试，但已经移除的任务不会回滚；MinIO 头像也未清理。可以进一步做持久化清理状态和重试任务，不能宣称现在已是分布式事务。

### 15 sendBeacon 是否保证埋点不丢

不能保证。true 仅代表浏览器排队成功，缺少服务端确认和持久化重试仍可能丢失。当前 SDK 登录后才注册访客，切账号先清空 visitorId、撤销旧注册，再用 revision 丢弃迟到结果，重点解决身份串写。

追问性能指标可靠吗：当前 LCP 在第一次回调后停止观察，可能不是最终值；其他指标也有采集时机限制。应说明具体采集方法，而不只报出五个指标名称。[MDN Beacon API](https://developer.mozilla.org/en-US/docs/Web/API/Beacon_API)

### 16 部署后首页正常，刷新子页面或模型资源失败怎么查

先区分路由与静态资源：History 页面刷新需要 index.html 回落；模型 URL 必须遵守 BASE_URL。当前页面挂 /english/，宿主代理去前缀后进入容器，API 保留 /api/v1 和 /ai/v1。

检查 URL、状态码、Content-Type 和真实响应；错误资源可能返回 index.html 并显示 200。构建通过只是第一步，要验证公开 URL 和实际页面交互。

### 17 你如何证明项目质量

按风险说明证据：支付测试验证重复通知和漏回调补偿；前端模拟测试验证角色切换、迟到响应和滚动；发音测试验证缓存、合并与失败路径；集成测试和浏览器验收补充真实依赖证据。

不编造 QPS、用户数、性能提升比例或线上稳定运行时长。没有测量就讲机制和测试边界，面试官通常更容易判断你是否理解实现。

**用户切换期间旧请求返回：** 先画 A 发请求、切 B、A 返回覆盖 B 的错误时序，再加入 revision 和提交前校验。补充 abort 只能减少浪费，不能承担全部正确性。

**注销期间邮件执行：** 画共享锁与独占锁竞争，以及 Redis、聊天库、业务库的清理顺序。指出哪一步失败可重试、哪些已完成动作不能事务回滚。

## 面试前最后核对

- 每个技术点都能打开源码讲出关键函数，而不是复述库定义。
- 区分已完成、代码中存在的缺口和自己提出的改进。
- 支付幂等不等于避免重复扣款；房间路由不等于鉴权。
- 双 Token 当前同为 7 天；业务模型为 13 个。
- 日报工具与普通 Chat 分开；搜索增强不冒充向量 RAG。
- 不把 Mock 测试说成真实支付、邮件或移动浏览器验收。
