# 埋点后端与访客数据生命周期

后端把访客身份与 PV、点击、性能、错误记录关联。当前产品埋点围绕登录账户展开，旧笔记中的“先匿名记录再绑定用户”已不符合 SDK 行为。

## 接收与存储

`/api/v1/tracker` 下有 uv、update-uv、pv、event、performance、error 六个 POST 端点。UV 先检查 userId 是否存在；缺失或用户已注销返回成功空值，不创建匿名访客。按 anonymousId upsert Visitor 后返回数据库 visitor.id。

PageView、TrackEvent、PerformanceEntry、ErrorEntry 都用 visitorId 外键关联 Visitor。注意：SDK 上报指纹构成的 anonymousId，后续事件使用服务端返回的 visitorId，两者不能混用。

## 账号注销并发

事件入库前检查 Visitor；它可能在检查后被账号级联删除。因此 record 方法只在捕获 P2003 且再次确认 Visitor 不存在时返回 false，其他错误继续抛出。这是明确处理可接受竞态，不能把任意异常都吞掉。

User 删除会级联删除 Visitor，再删除关联指标。已失效身份的迟到请求不会重新创建用户。这与前端登出立即停报配合，减少身份切换期间的数据串写。

## 当前能力边界

检查 body.userId 在数据库中存在，并不是验证调用方拥有该账号。TrackerController 当前未使用 AuthGuard，客户端上报字段也缺少完整运行时校验；因此不能声称这些分析数据具备可信身份认证。

Visitor 数量是存储的身份记录数，不自动等于某一天的 UV。按天 UV 需要在时间窗口内做访客去重；PV 是页面事件次数。匿名 ID 目前包含账户 ID，换账号会得到不同身份维度。

索引覆盖 visitorId/时间、path/时间、event/时间等查询场景，但是否有效要结合实际 SQL 和执行计划。不能从“建了索引”推导“性能提升了多少”。

## 练习

测试不存在的 visitor、写入前被删除的 visitor、合法 PV、其他数据库错误四种情况。扩展报表前先定义业务时区、统计窗口和去重键，再决定索引及数据保留周期。
