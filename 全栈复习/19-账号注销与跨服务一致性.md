# 账号注销与跨服务清理

注销不仅是删除 User，还要处理 Redis 任务和聊天检查点。当前方案通过账号锁和清理顺序降低并发问题，但不是跨数据库与 Redis 的分布式事务。

## 删除顺序

1. 入口是 DELETE /api/v1/user/me，身份取自 AuthGuard，确认文字必须精确为“注销账户”。
2. 获取账号独占 advisory lock；正在聊天或邮件任务时可能返回冲突，允许稍后重试。
3. 列举队列任务并筛选 userId，发现 active 邮件任务就拒绝，其他该用户任务逐个删除。
4. 连接 AI_DATABASE_URL，在聊天库事务中依次清理 checkpoint_writes、checkpoint_blobs、checkpoints。
5. 最后删除业务库 User，让外键级联清理学习、打卡、课程、支付、Agent、访客与关联埋点。

先清理外部资源再删账号，是为了外部步骤失败时保留用户作为重试入口。但前面已经删除的队列任务不会自动恢复，所以仍可能出现部分完成。

## 锁为何使用 PostgreSQL

AccountLockService 用同一个账号键调用 pg_try_advisory_lock 或 shared 版本。聊天与邮件相关动作持共享锁，注销持独占锁；多个进程通过数据库协调，比进程内 Map 更适合双后端应用。

锁属于专用数据库连接，action 完成后在 finally 解锁并释放连接。只接入该服务的操作受保护，不能声称系统所有写入都被锁住；共享锁之间也不互斥，所以它不是聊天线程串行锁。

## 历史清理的查询边界

thread_id 用精确前缀比较 `left(thread_id, length($1)) = $1`，userId 通过参数绑定传入。避免把 ID 放进 LIKE 通配模式，也避免字符串拼接用户输入形成 SQL。表名来自固定白名单，不来自请求。

Guard 在每次访问时查用户存在性，账号删除后旧 JWT 不能继续通过。埋点另外容忍 Visitor 被级联删除的竞态。

## 当前缺口与演进

MinIO 头像未清理；不参与账号锁的其他写流程仍需单独检查；任务列表全量扫描随队列增长会变慢。后续可以持久化注销阶段，以墓碑状态禁止新动作，配合可重试清理作业和审计结果。不要把这个改进说成当前已有 Saga。

现有测试覆盖确认文字、只清理当前账号、检查点失败保留账号和 active 邮件冲突。跨进程真实锁竞争还需数据库集成验证。
