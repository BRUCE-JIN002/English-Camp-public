# 课程权限与支付业务闭环

课程权限的真相在数据库，不在支付弹窗或 Socket 消息中。这个模块适合学习外部回调、事务、幂等和主动补偿如何组合。

## 从点击购买到获得权限

1. 登录用户提交 courseId。服务端查课程，并以数据库课程名和 Decimal 价格创建 PaymentRecord，不信任客户端报价。
2. 生成 `GK-` 加随机 ID 的 outTradeNo，通过 pageExecute 生成支付链接，支付窗口为 15 分钟。
3. 支付平台回调 notify。服务端验签并核对应用、订单、金额、交易状态等字段。
4. settle 在事务中有条件更新未结算订单，再 upsert 用户课程记录。
5. 事务提交后发送 paymentSuccess。浏览器通过状态接口确认并更新 UI。
6. 回调丢失时，status 查询支付平台并复用 settle 补齐本地权益。

随机订单号降低碰撞概率，数据库 outTradeNo 唯一约束负责最终拒绝冲突。不能用“随机所以绝不会重复”代替约束。

## 幂等如何发生

关键不是先查一次订单状态，而是事务内 `updateMany` 带“尚未成功”的条件。只有 count 大于 0 的请求继续授予权益；重复回调得到正常确认而不再次发通知。CourseRecord 的 userId/courseId 复合唯一键与 upsert 再限制重复权益。

支付平台、数据库和 Socket 不在同一个事务中。若数据库提交后通知丢失，查询接口能修复页面认知；事务本身不会保证 Socket 必达。

## 状态查询的边界

status 先查已购权益，再找用户最近 24 小时最多 20 个未支付订单，从对应课程中最多检查 3 个候选。支付平台查单失败返回业务 503 和“不要重复付款”的提示，不将未确认当作付款失败。

当前“我的课程”查询只接受关联订单 TRADE_SUCCESS，而 settle 接受 TRADE_SUCCESS 和 TRADE_FINISHED，存在展示语义不一致。新建订单前的已购检查也不阻止用户同时创建多个待支付订单；本地权益幂等不等于避免平台重复扣款。

## 复习检查

能解释“回调收到两次”“回调先到但浏览器断线”“支付成功但回调未到”“金额不符”分别走哪里。进一步可设计未支付订单复用、支付对账、退款和通知 outbox，但这些不能写成当前已完成。
