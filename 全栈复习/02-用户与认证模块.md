# 用户注册登录与资料更新

用户模块提供注册、登录、Token 刷新、资料更新、头像上传、统计读取和账号注销。账户身份应从服务端验证后的会话获取，不能信任请求体中的 userId。

## 注册和登录

注册先查手机号和可选邮箱是否存在，再创建用户，以 userSelect 排除密码等不应返回的字段，并签发两个 Token。登录按手机号查用户，比较传入 password 与数据库字段，成功后更新 lastLoginAt 并返回用户资料和 Token。

“先查再插”只改善错误提示，不能消除并发注册冲突；数据库 phone/email 唯一约束才是最后的防线。后续应把唯一冲突转成稳定业务错误。

服务端当前直接保存和比较传入的 password，没有服务端加盐慢哈希流程。即便客户端先做摘要，也不等于服务端安全密码存储；摘要仍可能成为可重放的登录凭证。不能写成“已实现安全密码加密”。

## 路由与身份

| 接口 | 用途 | 当前身份处理 |
| --- | --- | --- |
| POST /api/v1/user/register | 注册并签发 Token | 公开 |
| POST /api/v1/user/login | 登录 | 公开 |
| POST /api/v1/user/refresh-token | 刷新两个 Token | 校验 refreshToken |
| GET /api/v1/user/me | 当前资料与统计 | AuthGuard |
| POST /api/v1/user/update-user | 更新白名单资料字段 | AuthGuard |
| POST /api/v1/user/upload-avatar | 上传头像 | 当前未加 Guard |
| DELETE /api/v1/user/me | 注销当前账户 | AuthGuard 和确认文字 |

`getMe` 不重新签发凭证；前端同步资料时应保留现有 token。否则刷新统计可能覆盖会话。

## 定时提醒设置

开启提醒时检查有效邮箱和 HH:mm:ss 时间。资料先写数据库，随后向 AI 应用 `/ai/v1/digest/reschedule` 发请求。当前 fetch 没有等待最终成功，失败也被吞掉，因此“资料保存成功”不能证明“队列重排成功”。

还有部分更新的边界：变化检测拿旧值直接比较可能缺省的入参，重排请求也使用入参而非更新后的完整记录。可改为比较合并后的状态，返回可重试的调度结果，或使用 outbox 异步可靠派发。

## 练习和检查点

阅读 userSelect 与 updateUserSelect，说明为何不使用完整 User 返回登录结果；对资料同步做“请求发出后退出登录”的检查，确认迟到响应不能恢复旧用户。账号注销的跨库流程见第 19 篇。
