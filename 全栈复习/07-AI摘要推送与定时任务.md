# 每日学习摘要的生成调度与发送

日报分成“生成报告并排队”和“到时发送邮件”两段。这样发送不用阻塞用户页面，但也引入时区、重复任务、报告时效和失败补偿问题。

## 当前执行流程

DigestService 初始化时通过 upsertJobScheduler 注册 `EVERY_DAY_DIGEST_TASK`，cron 为 `0 0 * * *`。每日任务筛选开启提醒、时间非空、邮箱非 null 的用户；没有“当天必须学过单词”的筛选条件。

对每位用户创建带 queryTool 的 Agent。工具查询邮箱、名字、wordNumber 和当天新建的学习记录，模型生成 Markdown，再交 marked 转成 HTML。生成异常或无内容会退回提醒模板，然后按用户时间添加 EMAIL_DIGEST_TASK。

生成报告发生在入队前，延迟期间不重新读取学习记录；所以晚间收到的邮件可能基于更早的数据。失败模板写“今天还没开始学习”也不准确，因为 AI 故障同样会走这个分支。

## 时间与任务身份

jobId 为 `digest-${userId}-${YYYY-MM-DD}`，delay 是今天目标时刻减当前时刻，负数变为 0，而不是自动顺延到明天。调度日志写 UTC 零点，但配置没有显式 tz，Compose 又设置 Asia/Shanghai；不能凭日志断言真实触发时间。应为 cron 与日边界指定一致业务时区，并验证下次执行时间。

queryTool 使用 createdAt 范围，结束条件为 lte 次日零点，可能把次日边界记录算进今天；更清晰的区间是 `[当天零点, 次日零点)`。这属于改进方案，不是现有实现。

## 设置变更与消费

rescheduleUserDigest 按当天 jobId 找任务，关闭时删除，修改时间时先移除旧任务并尽量复用旧 HTML，再添加新任务。用户资料变更从主 API 通过内部 HTTP 触发它。

Processor 发送前重新检查用户存在，并在账号共享锁内调用 MailService；SMTP 失败会抛出，使任务失败。当前邮件任务未显式配置 attempts/backoff，不能声称具备自动多次重试。每日遍历也只在 AI 生成处捕错，某个用户入队失败仍可能中断后续处理。

## 改进与练习

把“到时读取学习数据、生成、发送”放进用户任务可改善时效；以用户和业务日期建立投递状态，区分生成失败、SMTP 失败和已发送。重试要防重复邮件，不能仅凭 jobId 宣称恰好一次。

DigestController 的 trigger/reschedule 当前没有 Guard，虽被当内部调用使用，代理仍转发 /ai 路径。内部 URL 命名并不等于网络隔离，需要服务间认证或路由限制。
